Project 1: SOC incident response, three shift reports

Three end-of-shift reports from a simulated security operations centre.

Triage, timelines and containment plans

Role: SOC analyst (simulated) · Deliverable: Word reports

The task

For each shift I reviewed the alerts, separated real threats from benign activity, reconstructed what happened, and wrote a report a manager could act on: executive summary, timeline, MITRE ATT&CK mapping, and recommended next steps.

Shifts

Shift 1: dropper on a workstation

A fake “design suite” zip led to a process tree masquerading as a legitimate application, with a dropped configuration file.

  • Recommended isolating the host and terminating the malicious process.
  • Recommended sweeping the wider fleet for the same indicators.
  • Recommended interviewing the user to find how the file arrived.
Shift 2: password spray to data exfiltration

The most complete attack chain I investigated:

  1. Password spray against the VPN, which had no MFA.
  2. Credential dump from LSASS.
  3. Lateral movement to a domain controller.
  4. About 500 MB of finance data exfiltrated.
  5. Persistence through a rogue admin account, a SYSTEM scheduled task, and RDP enabled.

Each step was mapped to MITRE ATT&CK.

Shift 3: ransomware over SMB

Ransomware spread over SMB to three hosts. I traced patient zero to a dormant scheduled task left behind by an earlier intrusion, and explained why the patch reboot only triggered it rather than caused it.

Containment was ordered by urgency: isolate hosts, block command-and-control, pause the patch rollout, preserve evidence, then remediate.

What I learned

Alert triage, timeline reconstruction, root cause analysis, prioritising containment, and writing for both technical and non-technical readers.

Project 2: Malware analysis, static and dynamic

A full analysis of a provided Windows sample, in an isolated lab.

.NET remote access trojan (AsyncRAT/XWorm family)

Role: malware analyst · Deliverable: static report, dynamic report, IoC bundle

Safety setup

All work was done in an isolated Windows 10 VM with a clean snapshot, host-only networking, and monitoring from System Informer, Wireshark and Regshot. The sample was never run on my own machine.

Static analysis

  • Identified the file type by signature rather than extension.
  • Calculated MD5, SHA-1 and SHA-256, then checked VirusTotal and MalwareBazaar, which pointed to the AsyncRAT/XWorm family.
  • Reviewed PE headers, compile timestamp, section entropy and the import table.
  • Found a string suggesting an anti-sandbox hosting check.
  • Concluded the sample relied on managed-code obfuscation instead of a native packer.

Dynamic analysis

No execution was observed in the lab. I troubleshot the environment (including the .NET runtime) and documented two possible explanations with confidence levels, rather than claiming behaviour I hadn’t seen.

Outputs

An indicator-of-compromise table, a STIX 2.1 bundle, a MITRE ATT&CK mapping, and detection recommendations.

Project 3: Web application penetration test

NahamStore, an intentionally vulnerable shop on TryHackMe.

10 confirmed vulnerabilities with a remediation roadmap

Role: penetration tester · Deliverable: findings deck · Standards: OWASP Top 10, CWE

Result

7 High3 Medium

Every finding includes the request, the payload, the business impact, its CWE and OWASP mapping, and a specific fix.

Findings

  • Reflected and stored cross-site scripting (XSS)
  • Two open redirects
  • Two insecure direct object references (IDOR)
  • Cross-site request forgery (CSRF), with a token that was not enforced
  • Server-side request forgery (SSRF), including a filter bypass
  • Local file inclusion through path traversal
  • XML external entity injection (XXE)

Attack chains

I showed how an open redirect, an IDOR and stored XSS can be combined to take over accounts and expose data, which matters more than any single bug on its own.

Roadmap

Fixes were grouped into 7-day, 30-day and 90-day actions so the client could prioritise.

Hands-on experience: virtualized home lab

A three-machine lab I built and tested myself, covering the setup and troubleshooting skills behind IT support work.

Windows Server, Windows 11 and Ubuntu on an isolated network

Role: lab builder and administrator · Platform: VMware Workstation Pro 17.6 · Host: Windows 10 Home, 8 GB RAM

The task

Build a small virtual network to practise IT support and security work: install three operating systems, put them on one private network, and prove they can communicate. Every screenshot below comes from my own lab.

The lab

The host has about 8 GB of RAM, so memory is shared carefully between the three VMs.

Build and proof

Installation media and VMware Workstation

I downloaded Windows Server 2022 (about 5.7 GB), Windows 11 Enterprise (about 7.7 GB) and Ubuntu 26.04.1 Desktop (about 6.0 GB), then installed VMware Workstation 17 Pro, version 17.6.4. The Windows images are Microsoft evaluation editions, so they expire (90 days for Windows 11, 180 days for Server).

Lab network

In the Virtual Network Editor, VMnet8 (NAT) uses the 10.10.10.0/24 subnet with the local DHCP service enabled. NAT gives the VMs internet access on a private network, and a fixed range keeps addresses predictable.

Windows 11 client

The client runs Windows 11 Enterprise Evaluation with a local account, 4 GB of RAM and 2 virtual processors. The watermark confirms the edition and a 90-day license.

Ubuntu machine

I installed Ubuntu Desktop and checked the machine name from the terminal.

Windows Server

I installed Windows Server 2022 Standard with the desktop experience (evaluation license valid for 180 days) and renamed it SVR01. It stays in the default workgroup, and its IPv4 address comes from DHCP.

Connectivity tests

I pinged between the machines to prove they can talk to each other over VMnet8.

Snapshots

After the connectivity tests I took a VMware snapshot of each VM, so every machine has a known-good state to return to if a later project breaks it. The Snapshot Manager shows one snapshot per VM, taken on 12 November 2026.

Problem and fix

The first ping from Ubuntu to 10.10.10.129 (Client01) failed: 11 packets sent, none received. Windows Defender Firewall drops inbound ICMP echo requests by default. I allowed them with a firewall rule on that machine, and the retry succeeded with 0% loss.

New-NetFirewallRule -DisplayName "Allow ICMPv4" -Protocol ICMPv4 -IcmpType 8 -Action Allow

What I learned

  • A failed ping does not always mean a network fault, because the Windows firewall blocks it by default.
  • The TTL in a reply hints at the operating system: 128 from the Windows machines, 64 from Ubuntu.
  • A dedicated NAT subnet with DHCP keeps a lab predictable.
  • Evaluation licenses expire, and snapshots give each VM a known-good state to return to.

Hands-on experience: Active Directory and Group Policy

I turned the lab server into a domain controller, joined the Windows 11 client to the domain, and enforced a policy on a domain user.

A working domain with users, groups and policies

Role: systems administrator (lab) · Platform: Windows Server 2022 and Windows 11 on VMware Workstation Pro

The task

Build an Active Directory domain from scratch: give the server a fixed address, install and promote the domain controller, make DNS work for the domain, create an OU structure with users and groups, join a client, and apply Group Policy.

The domain

ItemDetail
Domainlab.internal (NetBIOS name LAB)
Domain controllerSVR01, 10.10.10.10 (static), also runs DNS
Member computerClient01, 10.10.10.129 (DHCP)
StructureLabCorp OU with Users, Group and Computers
UsersAva Brooks, Noah Khumalo, Mia Jacobs (fictional)
PoliciesAccount lockout (Default Domain Policy), Lab-restrict settings

Build and proof

Static IP and internet check

A domain controller needs a fixed address and must use itself for DNS. I set SVR01 to 10.10.10.10 with the VMware NAT gateway (10.10.10.2), then confirmed it with ipconfig and a ping to the internet.

Install AD DS and promote SVR01

I added the Active Directory Domain Services role (with Group Policy Management and the AD tools) and promoted SVR01 to a domain controller for the domain lab.internal (NetBIOS name LAB). The only warning in the prerequisites check was about DNS delegation, which a lab with no parent DNS zone can ignore.

DNS forwarder

SVR01 also runs the domain’s DNS. I added 8.8.8.8 as a forwarder so the lab can still resolve internet names.

OUs, users and groups

I created an organizational unit called LabCorp with Users, Group and Computers OUs inside it, three fictional users and a security group, so policies can be linked to the right place.

Join Client01 to the domain

Client01 received 10.10.10.129 from DHCP, and I pointed its DNS at the domain controller. The domain name resolved, the join succeeded, and I signed in as a domain user. I then moved the computer account into LabCorp\Computers.

Group Policy

In the Default Domain Policy I reviewed the password policy and set an account lockout of 5 invalid attempts. I then created a separate GPO, Lab-restrict settings, that blocks Control Panel and the Settings app for users in the LabCorp Users OU, and proved it applied to abrooks.

Snapshots

After everything worked I took an “After AD” snapshot of SVR01 and Client01 on 14 November 2026, so each machine has a known-good state to return to.

What I learned

  • A domain controller needs a fixed IP and must be the DNS server for its clients, and a domain join only works if the client can resolve the domain name.
  • Group Policy follows where the user sits: the GPO linked to the LabCorp Users OU applied to abrooks, and gpresult /r proves it.
  • Checking beats assuming: nslookup and gpresult show what is working before I rely on it.
